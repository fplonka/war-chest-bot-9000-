# v5_sweep_normal_gate

We were isolating the high-priority trainer experiment from `v5_sweep_priority_gate`. This run used the same strong initializer, seed, no-warmup schedule, two-card solver settings, and tuned cooperative-sweep grids, but put PyTorch back on the normal-priority CUDA stream.

Normal priority did not restore the lost throughput. The run completed 152,766 solves and 610,304 optimizer rows in 307.6 seconds, for 496.0 balanced solves/s including drain. The high-priority run reached 479.9/s, so normal priority was only 3.4% faster. There were zero drops and zero exact CPU fallbacks, and the final debt was only 760 rows. The opening again reached about 1,500/s before recent throughput fell to roughly 300--400/s. The first completed game appeared in the 80--81 second report and 451 games finished overall.

The control changes the interpretation of the previous run. Stream priority made fitting much faster under contention (about 19 seconds of accumulated training wall time versus 65 seconds here), but generation is dominated by the other solve card and by increasingly expensive game positions, so preemption had little overall effect. The no-warmup trajectory, not trainer priority, explains most of the gap from the earlier 762/s gate that included five minutes of Greedy value warmup. Even an initializer that already beats Greedy benefits from that phase: it changes early values enough for games to finish sooner and avoids the especially costly trajectory seen here.

Average utilization was 55.9% on GPU 0 and 53.2% on GPU 1; peak memory was 17,793 MiB and 20,105 MiB. The run finished 451 games, routed 398 oversized waves, hit the configured node cap 2,448 times, and censored the expected 4,608 actors at shutdown. At this point the separate sweep-grid defaults remain a measured frozen-workload improvement, while trainer priority remains optional and defaults to normal. The next performance work should use an aged or post-warmup workload rather than cheap opening roots.
