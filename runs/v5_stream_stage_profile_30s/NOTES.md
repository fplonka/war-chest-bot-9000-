# Integrated trainer stage profile

We were timing the real continuous trainer from inside the shared process, including the actual replay batches rather than the older frozen sample. CUDA event timing was enabled only for this diagnostic. It used the published warm checkpoint, two RTX 3090s, 36 builders with 96 actors each, and a 30-second fixed budget with ten seconds reserved for drain.

The missing cost is both wider live data and contention. During the first active interval, a training batch averaged 43,881 configurations; 32 steps spent 5.57 seconds preparing rows and copies and 3.64 seconds in measured GPU forward/backward work, for 9.38 seconds total. The next interval sampled an unusually broad part of replay at 101,136 configurations per batch; 48 steps spent 5.19 seconds preparing and 2.86 seconds on GPU work, for 8.57 seconds total. After GPU admission stopped, batches narrowed to 46,457 configurations and 26 steps took only 1.96 seconds, including 0.39 seconds of GPU work. The older isolated sample averaged only 30,753 configurations per batch, so it understated production expansion. More importantly, the same model math falls back near its isolated 15 ms/step as soon as solve kernels stop competing for GPU 1.

The run counted 27,152 solves and 108,544 optimizer rows, leaving 64 rows of debt. It reported 905.2 balanced solves/s over the fixed 30 seconds, with zero large-job routes, exact fallbacks, node-cap events, or drops; all 3,456 live games were censored at shutdown. At this point correctness and accounting remained sound. The performance work should target fast matrix math/GPU scheduling and moving variable-width row expansion off the contended host path, rather than adding PyTorch CPU threads.
